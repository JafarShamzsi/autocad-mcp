# autocad-mcp Audit — 2026-05-11

Scope: full repo at HEAD (12 MCP tools, 3 backends, project model with
SCHEMA_VERSION=5, AutoLISP reactor event source, Claude Code plugin
packaging). 367 default + 12 integration tests passing.

Each finding has: **category · severity · location · description · suggested fix**.

Severity rubric:
- **HIGH** — security risk, data corruption, or shipping-blocker for real users.
- **MED** — real bug, real gap, or quality issue that will bite a maintainer.
- **LOW** — polish, nice-to-have, or non-obvious-but-not-urgent.

## Critical Issues (HIGH severity)

### H1. `execute_lisp` is unrestricted code execution
- **Category:** SECURITY · **Files:** `backends/com_backend.py:1405`, `backends/file_ipc.py:299-309`, `server.py` `system` tool dispatch
- **Description:** The `system(operation="execute_lisp")` operation passes arbitrary LISP straight to `Document.SendCommand(...)` (COM) or writes it to a temp file that AutoCAD loads (file_ipc). No input validation, no sandboxing, no allow-list. A malicious or buggy LLM client can erase drawings, delete files via `(vl-file-delete ...)`, change system variables, or run any LISP the user's AutoCAD supports.
- **Fix:** Either (a) document the risk prominently in the tool's docstring + the README and require an `AUTOCAD_MCP_ENABLE_LISP_EXEC=1` env var to enable it, or (b) restrict to an explicit allow-list of LISP primitives. The existing LISP dispatcher's command-whitelist pattern is the right shape.

### H2. Schema migration is a hard wall, not a path
- **Category:** GAP · **File:** `project/index.py:188-219`
- **Description:** `init_db` raises `SchemaVersionMismatch` for **any** version mismatch (older OR newer) and tells the user to delete + re-index. There's no actual migration. When SCHEMA_VERSION bumps (we're at 5 from 1), every existing user's `.acadproj.db` becomes unreadable until they re-index — which loses any annotations stored only in the db (today: none, but a future slice could add them). The strict guard is *better* than silent wrong answers, but it's not a long-term migration story.
- **Fix:** Either commit to "the db is a derived cache, always rebuild on version mismatch" (then auto-rebuild instead of erroring), or add an ALTER-TABLE migration table keyed on version pairs. The first is simpler and matches reality today.

### H3. `find_drawings` / `find_entities` swallow LIKE injection through `dwg_file`
- **Category:** SECURITY · **File:** `project/query.py` `find_sheets_for_drawing`
- **Description:** The query builds `LIKE ?` with `f"%/{drawing}"` as the param. If `drawing` contains `%` or `_`, those are LIKE wildcards and the match is broader than the user expects. Not a security risk against the local SQLite (caller's own data), but a correctness bug — searching for `"_DETAIL.dwg"` would match `"AB-DETAIL.dwg"` unintentionally.
- **Fix:** Escape `%` and `_` in the input before building the LIKE pattern, or split into exact + suffix queries with proper escaping.

### H4. `file_ipc` PostMessage trigger doesn't work on full AutoCAD 2027
- **Category:** BUG · **File:** `backends/file_ipc.py:216-244`
- **Description:** Already documented in memory but worth surfacing: the `PostMessageW(WM_CHAR)` keystroke trigger to MDIClient (designed for AutoCAD LT) fails to reach the command line on full AutoCAD 2027 — even when the dispatcher is confirmed loaded via direct probe. The cmd-file/result-file protocol itself works; only the trigger is fragile.
- **Fix:** Investigate WM_KEYDOWN/WM_KEYUP instead of WM_CHAR, re-find the MDI client HWND per dispatch, or add a small .NET helper exposing a named-pipe trigger. Verify LT 2024+ still works after any change.

## Significant Gaps (MED severity)

### G1. `arch_wall_with_openings` not wired to file_ipc/LISP
- **Category:** GAP · **File:** `lisp-code/mcp_dispatch.lsp` (LISP side missing this command)
- **Description:** The Python primitives + COM + ezdxf backends all support `wall_with_openings` (auto-cut walls around doors/windows). The file_ipc backend / LISP dispatcher has the simpler primitives (`arch-wall`, `arch-door`, etc.) but not the composite. LT users have to chain calls.
- **Fix:** Port the wall-segment + opening-loop logic from `arch/geometry.py::wall_segments_with_openings` to a new LISP handler `mcp-cmd-arch-wall-with-openings`. ~50 lines of LISP.

### G2. ezdxf backend missing `entity_offset` and `entity_array`
- **Category:** GAP · **File:** `backends/ezdxf_backend.py:317-322` (offset), no array
- **Description:** Both operations return "not supported on ezdxf backend". COM + file_ipc support them. Cross-backend behavioural inconsistency that surprises callers.
- **Fix:** `entity_array` is straightforward (duplicate + translate; ezdxf has a `copy()` method on entities). `entity_offset` is harder for arbitrary curves; punt to LINE-only as a starter (parallel offset is just the perpendicular-translate trick already used in `wall_corners`).

### G3. `library_define` for file_ipc/LISP is stubbed
- **Category:** GAP · **File:** `backends/file_ipc.py` (no library_* methods)
- **Description:** The symbol library (toilet, sink, north arrow, etc.) works on COM + ezdxf. file_ipc users get the default "not supported" from the base class. LT users can't use the procedural library.
- **Fix:** Add LISP handlers that walk the same `SYMBOL_LIBRARY` data and call `(command "_BLOCK" ...)` with the entity spec. Same shape as the arch primitives.

### G4. Dim/textstyle compliance check missing from `check_standard`
- **Category:** GAP · **File:** `project/standards.py`
- **Description:** `LayerStandard` only checks layers. Dimstyle and textstyle drift detection exists (`find_style_inconsistencies`) but isn't part of the standard-compliance flow. A firm with a `firm-standard.dxf` that defines dimstyles can't say "every drawing should match these dimstyles."
- **Fix:** Extend `LayerStandard` → `Standard` with `dimstyle_rules` and `textstyle_rules` lists. Reuse the existing dimstyle/textstyle indexer rows.

### G5. Live LISP verification for `mcp_reactors.lsp` deferred
- **Category:** TEST · **File:** `lisp-code/mcp_reactors.lsp`
- **Description:** The Phase 3 reactor file ships with parse-tests that grep for the expected keywords, but no test exercises a reactor *actually firing*. The silent-failure mode (mistyped reactor keyword, never fires, no error) is the most likely class of bug — and the parse-test catches typos but not semantic mistakes.
- **Fix:** Add a manual-smoke checklist in `docs/` for an architect to run on first install (load reactor, draw a line, verify event log gets a record). Or, more ambitious: build a `pytest -m integration` test that drives the COM backend, attaches reactors, draws something, then asserts the event log has the right record.

### G6. Sheet-set reader untested against real `.dst` from AutoCAD
- **Category:** TEST · **File:** `project/sheetset.py`
- **Description:** Tests use synthetic `.dst` XML I wrote by hand. AutoCAD's actual `.dst` format has more variation than my fixture exercises (subset hierarchies, callout references, ResourceId graph patterns). The reader is "tolerant by design" but unverified against the real thing.
- **Fix:** Have AutoCAD generate a real `.dst` (SHEETSET command → New) and add it as a golden fixture, then assert basic shape (sheet count, has DWG references).

## Quality Issues (MED severity unless noted)

### Q1. Broad `except Exception: pass` patterns in 30+ places
- **Category:** SMELL · **Files:** com_backend.py (×10), ezdxf_backend.py (×2), file_ipc.py (×1), server.py, screenshot.py (×3), config.py, arch/layers.py, arch/primitives.py, project/index.py
- **Description:** Some are legitimate best-effort cleanups (close on teardown, ignore failure). Many silently swallow real failures with no log breadcrumb. Hard to debug when things go wrong — the COM screenshot init in particular masks ImportError, AttributeError, and COM RPC failures with identical `pass`.
- **Fix:** Replace blanket passes with `log.debug("operation_X_failed", error=str(ex))` for diagnostic visibility. Keep the no-raise behavior where it's intentional (best-effort cleanup) but always log.

### Q2. ezdxf upper bound missing in pyproject.toml
- **Category:** SMELL · **File:** `pyproject.toml:10`
- **Description:** `ezdxf>=0.18` with no upper bound. ezdxf 2.x would likely break our `add_lwpolyline(... dxfattribs=...)` and other internals.
- **Fix:** Add upper bound: `ezdxf>=1.0,<2.0`.

### Q3. `LayerRule` defaults are asymmetric
- **Category:** SMELL · **File:** `project/standards.py:38-40`
- **Description:** `expected_color: int | None = None` (don't check) vs `expected_linetype: str | None = "CONTINUOUS"` (silently enforces CONTINUOUS as default). A firm that wants to check only colors can't omit linetype without explicitly setting it to None.
- **Fix:** Default both to `None`; `load_standard_from_dxf` and `aia_standard` should set explicit linetypes for each rule. Caller-controlled, not framework-defaulted.

### Q4. Hardcoded `C:/temp` default for IPC dir
- **Category:** SMELL · **File:** `config.py:15`, `events.py`, LISP files
- **Description:** Falls back to `C:/temp` if `AUTOCAD_MCP_IPC_DIR` isn't set. Hardcoded on a directory that may not exist on a fresh Windows install. The dispatcher creates it on demand, but the user-facing UX is "why is autocad_mcp_*.json showing up at C:/temp?".
- **Fix:** Default to `Path(tempfile.gettempdir()) / "autocad-mcp"`. Document in the README that this is configurable. The LISP side already reads `*mcp-ipc-dir*` so the default just needs to match.

### Q5. Inconsistent error message format across backends
- **Category:** SMELL · **Files:** Multiple
- **Description:** Errors come back as bare strings with varying conventions: `"Not supported on this backend"` vs `"Offset not supported on ezdxf backend"` vs `"Entity not found"` vs `"chamfer via COM not yet implemented..."`. The `_error()` helper in client.py does substring-matching to attach hints; small wording changes silently break hints.
- **Fix:** Standardize error shapes — at minimum, a `category` enum (`not_supported`, `not_found`, `invalid_arg`, `backend_unavailable`). Hints attach off the category, not substring matching.

### Q6. Discipline-by-substring in sheet set XML parsing is over-broad
- **Category:** SMELL · **File:** `project/sheetset.py:_NON_SHEET_CONTAINERS`
- **Description:** The container exclusion set is hand-curated. Future AutoCAD versions might add new container element names (e.g., `AcSmSheetSubset` is mentioned in some docs but isn't in the exclusion set). The current parser would falsely classify a new container as a sheet.
- **Fix:** Once a real-world `.dst` corpus exists (G6 fix), audit the actual element names and either expand `_NON_SHEET_CONTAINERS` or invert the criterion — "must be exactly `AcSmSheet` or `Sheet`, AND must have a FileName descendant".

### Q7. COM library `entity_count` value unverified
- **Category:** TEST · **File:** `backends/com_backend.py::library_define`, `tests/test_com_integration.py`
- **Description:** Already documented in slice #6: `block.Count` in COM was added but the strengthening test `test_entity_count_in_define_payload_matches_spec` couldn't run end-to-end because AutoCAD was saturated. Currently unverified.
- **Fix:** Run the test once on a fresh AutoCAD restart; the test is already in place, just needs to pass once to confirm the assertion holds.

### Q8. `door_geometry` ambiguous when `room_side` is on the closed-door axis
- **Category:** SMELL · **File:** `arch/geometry.py:door_geometry`
- **Description:** When `room_side` lies exactly on the line of the closed door (cross product = 0), the resolved swing falls through to whatever the caller passed in `swing`. Not documented; might surprise callers who passed `room_side=(0,0)` thinking it would be auto-resolved.
- **Fix:** Raise ValueError or pick a deterministic side (e.g., always default to "left") and document the tiebreak rule in the docstring.

### Q9. `EventTail.read_recent` reads the whole file
- **Category:** SMELL · **File:** `events.py:read_recent`
- **Description:** Iterates the entire log every call to get the last N lines. For a long-running session with thousands of events, this is O(file size) per call. The byte-offset cursor in `read_new` avoids this, but `read_recent` doesn't use a reverse-scan or seek.
- **Fix:** Seek to a heuristic position (e.g., `file_size - limit * 200 bytes`) and parse forward from there. Document the heuristic.

## Documentation Gaps (LOW–MED severity)

### D1. SECURELOAD / TRUSTEDPATHS not in the load instructions
- **Category:** DOC · **File:** `README.md` Quick Start
- **Description:** Loading `mcp_dispatch.lsp` from an arbitrary repo path in modern AutoCAD (with SECURELOAD=2) prompts a security warning the user has to accept. Real users will trip on this and not know it's expected.
- **Fix:** Add a "Trusted paths" subsection: either (a) add the repo to TRUSTEDPATHS, (b) set SECURELOAD=0 temporarily, or (c) click "Load" through the prompt.

### D2. `accoreconsole.exe` version-specific behaviour
- **Category:** DOC · **File:** `project/dwg_reader.py::_convert_with_accoreconsole`
- **Description:** Already noted in a code comment: the DXFOUT prompt sequence is verified against AutoCAD 2026/2027 only. Older AutoCAD installs may prompt differently. The README mentions "AutoCAD installed" generically.
- **Fix:** Add a "DWG support requires AutoCAD 2018+ (the DXFOUT prompt sequence used by `accoreconsole.exe` matches that version range)" note to the README's DWG section.

### D3. File-IPC ↔ full-AutoCAD limitation undocumented
- **Category:** DOC · **File:** `README.md`
- **Description:** The PostMessage trigger doesn't reliably work on full AutoCAD 2027 (H4). The README doesn't say so — users who set `AUTOCAD_MCP_BACKEND=file_ipc` against full AutoCAD will see init succeed (window found) but every command time out (no result file).
- **Fix:** Add a sentence to the backend table: "file_ipc backend is designed for AutoCAD LT. Use the COM backend for full AutoCAD; auto-detection prefers COM when full AutoCAD is detected."

### D4. SCHEMA_VERSION bump process not documented
- **Category:** DOC · **File:** `project/index.py:42`
- **Description:** Next maintainer who needs to add a column has to figure out: bump SCHEMA_VERSION? Add ALTER? Both? Add a migration test? No checklist.
- **Fix:** Add a comment block above `SCHEMA_VERSION` with the bump checklist: (1) bump constant, (2) add new tables/columns to `_SCHEMA`, (3) add an entry to the migration table when H2 is fixed, (4) add a regression test using a v(N-1) fixture.

### D5. CC0 marker only in symbols.py, not at repo root
- **Category:** DOC · **File:** `LICENSE` (MIT) vs `arch/library/symbols.py` (CC0 in docstring)
- **Description:** The repo LICENSE is MIT. The symbol library inside it is CC0 (per the docstring). Mixed-license projects need a clearer signal. A forker reading just LICENSE won't realize the symbols are CC0.
- **Fix:** Add a sentence to LICENSE / NOTICE noting that `src/autocad_mcp/arch/library/symbols.py` is CC0 specifically.

## Forward-Looking Recommendations

Not bugs or gaps — direction-of-travel improvements that would raise the bar.

### F1. Consider a `tools.json` MCP manifest
The plugin format lets us declare tools statically — that would unblock per-tool permission grants (e.g., `system.execute_lisp` requires user confirmation, others don't).

### F2. Add a `claude_install.md` quickstart inside the plugin
After `claude plugin install ...`, the user lands in a fresh repo with no concrete first task. A 5-line "try this first" file would close the gap between install and first useful command.

### F3. Live integration tests as part of CI (or a one-shot script)
The `pytest -m integration` suite needs a running AutoCAD. Currently developers run it manually. A `scripts/run_integration.ps1` that fresh-launches AutoCAD, runs the suite, closes the docs, and exits would make this routine.

### F4. Bench the indexer
SQLite reads are fast, but the indexer walks every entity in every drawing. A 200-DWG project hasn't been bench tested. Adding a `pytest-benchmark` test that indexes a synthetic 50-drawing project would give a baseline.

### F5. AutoLISP reactor → .NET reactor as a Phase 3 v2
The current Phase 3 ships via AutoLISP reactors (good: no .NET build; bad: limited event surface, can't subscribe to selection changes cleanly). The original analysis flagged .NET as the richer path. The event-log file format is intentionally generic — a future .NET reactor writes the same JSON-lines and `EventTail` works unchanged.
